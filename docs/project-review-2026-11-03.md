## 已修复问题

### 波峰计价设置校验不一致

后端原先允许 `09:00–12:00` 与 `11:00–14:00` 同时保存，前端却拒绝这一组合。时间解析使用 `fmt.Sscanf`，还会接受 `09:00suffix`、`9:00`、`09:0` 等不完整的 `HH:MM` 值。

新增回归在原实现上复现了重叠时段及畸形时间被接受。现在：

- 后端要求完整的 `HH:MM`，使用固定格式解析，正常路径不产生堆分配。
- 开启波峰计价时拒绝重叠；允许首尾相接、两段顺序互换。
- 输入校验后补齐默认设置，再校验生效值，避免缺省第二段与第一段重叠。
- 校验失败返回 Admin HTTP `400`；内存值和已保存文件均不变。
- 旧文件中的无效波峰配置沿用加载失败后的默认值回退与日志机制；手工配置应使用上述格式。

对应实现是 `internal/usagestats/settings_validation.go` 与 `settings_store.go`。HTTP 回归在 `internal/httpapi/admin/usage/handler_test.go`。中英文 API 文档已同步。

## 性能优化与测量

### 流式字面量边界扫描

旧 Go 实现在每个注释 / CDATA 正文字节上执行字符串拼接；Node 对每个字符拼接、截取，并逐字符运行 CDATA 正则。66,000 字节正文在 Go 扫描器中产生约 66,000 次堆分配。

新实现直接搜索当前块，另检查跨块闭合符。Go 仅保留四字节固定缓冲，Node 仅保留两个 UTF-16 单元。引用字符串仍使用既有转义状态；完整正文仍由原缓冲与权威解析器拥有，不在扫描器中复制。

回归覆盖 ASCII 及 `＞` / `﹥` / `〉` 闭合符的全部拆分位置、空块、伪前缀、长正文、引号转义、JSON 控制字符、EOF 和字面量之后的真实工具调用。Go 按字节拆分，能够覆盖 Unicode 多字节字符内部的边界。

### 用量数据计算

`aggregateDaily` 原来对每一条记录调用 `parseDayKey`，即使当天的聚合桶早已存在。现在每个日期仅在首次建立桶时解析一次，并与补齐空日期共用一个桶结构定义。

每模型卡片的 token / cost / calls 合并到一次遍历；派生计算移入 `useUsageDashboard`。全量账本总数单独按 `records` 缓存，切换筛选条件时不再重新遍历完整账本。各维度计数、费用、GMT+8 日期边界、原型属性名和图表有限分桶继续由回归测试覆盖。

## 第二轮：账本轮询、检查点与设置保存

本轮在第一轮工作区继续修改，保留此前的优化与回归。

### 复现与修复

实际 React Hook 的六个初始回归在修复前全部失败：

- 保存响应、JSON 解析或错误迟到，会覆盖或关闭已经重开的设置弹窗。
- 组件卸载后，旧保存仍会发出成功消息。
- 注入的 fetch 同步抛错时，旧 finally 先清空引用，随后外层又写回已完成 Promise，导致后续重试不发送请求。
- 弹窗重开后，第二次保存被旧的在途 Promise 阻挡；旧 finally 也无法区分新旧操作。

`useUsageSettings` 现为每次保存建立请求身份，并记录弹窗世代。打开、关闭、请求来源变化或卸载会取消旧操作；接受响应前、读取 JSON 后与 finally 都检查当前身份。操作引用先发布，再异步调用 fetch，避免同步异常留下失效 Promise。完成回调也必须仍属于当前弹窗才可关闭它。旧读取在保存开始时失效，避免随后覆盖已接受的保存。请求体构造移入 `usagePricing.toServerUsageSettings`，显式零价格及默认值口径保持一致。

复核还发现 `DashboardShell.authFetch` 依赖翻译函数，切换语言会重建所有下游请求来源。现通过引用读取最新鉴权文案，回调仅在 token 或退出处理器改变时更新，避免语言切换触发重载或取消正在保存的操作。

新增 `react-test-renderer` 18.3.1 为开发依赖，与现有锁定的 React 版本匹配。9 项实际 Hook 回归覆盖上述问题、重复保存复用、零价格，以及用量 Hook 的 304 / 清空 / 切换来源；7 项纯资源回归覆盖迟到响应、迟到 JSON、错误、取消、卸载及验证器归属。它们均已接入全量 Node 入口。

### 未变化账本的条件读取

原来的 `/admin/usage` 每次都会复制并排序全部条目，再编码完整 JSON。前端虽然会比较数组并复用旧引用，仍然支付了网络传输、JSON 解析和条目转换开销。

`usagestats.summary.go` 现在提供业务版本及与版本一致的快照。条目副本和版本在同一把锁下读取；排序继续在锁外进行。实例随机身份使进程重启后不会复用计数相同的旧版本。HTTP 层把版本格式化成弱 ETag；匹配 `If-None-Match` 时直接返回无正文的 `304`，支持验证器列表、强弱比较与通配符。

前端 `usageRecordsResource` 只保存已接受数据的 ETag。过期响应和解析不能污染版本；清空记录会取消旧读取并移除验证器；切换 fetch 来源会处置旧资源，旧刷新回调不能重新启动请求。304 不读取 JSON，保留原数组引用。失败保留现有数据及其验证器。没有 ETag 的成功响应仍兼容，并清除旧验证器。

记账、成功导入、清空均使版本变化；后台落盘不改变业务版本。读取快照与版本的并发一致性、返回副本的隔离、重启失效及 HTTP 304 行为均有回归。

### 检查点编码

用量账本的每次脏 flush 仍然保留原有单写入串行化、revision 检查、原子替换和失败重试。将 `MarshalIndent` 改为 `Marshal`，减少缩进扫描及写盘字节，文件版本和字段不变，已有文件仍可直接读取。

检查点测试验证紧凑 JSON 的结构与数值、失败 flush 的重试，以及干净账本不重复写入。本轮未引入异步写入队列或增量日志。
